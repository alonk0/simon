### 1.1 נימוק הבחירות והחלופות שנבחנו

- **Frontend:** נבחנו Vanilla TypeScript, React ו־Vue. React ו־Vue בשלות, מתועדות ונפוצות, אך למשחק ממוקד עם שני מסכים, מצב קטן וללא שרת, Vanilla TypeScript מפחית תלויות ומורכבות ומנצל APIs סטנדרטיים; TypeScript מעניק טיפוסים מפורשים שמסייעים גם לפיתוח באמצעות AI. אין צורך ב־Next.js, SSR או ניהול מצב חיצוני. React עשוי להתאים למוצר מורכב יותר, אך אינו מוסיף ערך מספק כאן.
- **Build:** נבחנו Vite, Parcel ו־Webpack. נבחר Vite בשל תצורה מצומצמת, תיעוד פריסה רשמי ל־GitHub Pages ואימוץ רחב; אין צורך בהגדרות Webpack ייעודיות.
- **PWA:** נבחנו Service Worker ידני, `vite-plugin-pwa` ופתרון PWA במסגרת Framework. התוסף הנבחר מפיק Manifest ו־precache של נכסי ה־Build ומקטין את הסיכון להחמיץ קבצים הנחוצים ל־Offline. במוצר קטן נעדיף `generateSW` על כתיבת Service Worker מותאם אישית.
- **צלילים:** נבחנו Web Audio API, קובצי שמע מקומיים וספריית אודיו חיצונית. צלילים סינתטיים קצרים באמצעות Web Audio API מספקים ארבעה גוונים שונים, אינם דורשים הורדות נוספות או רישוי לקובצי אודיו, ומשתלבים עם Offline. אין צורך בספריית שמע.
- **אחסון:** נבחנו `localStorage`, IndexedDB ואחסון שרת. ה־PRD מחייב `localStorage`; היקף הנתונים קטן, קריאתו פשוטה ואין צורך בסנכרון. סטטיסטיקות יחושבו מההיסטוריה כדי למנוע חוסר עקביות.
- **Hosting:** נבחנו GitHub Pages, Netlify ו־Cloudflare Pages. GitHub Pages מתאים ישירות לאתר סטטי, משתלב ב־GitHub Actions ומייתר שירות Hosting נוסף. אין צורך ב־Vercel או Supabase.

**אימוץ ובשלות:** ממשקי הדפדפן הנבחרים מתועדים ב־MDN ונתמכים באופן רחב. נתוני State of JS 2025 מצביעים על שימוש נרחב ב־Vite וב־Frameworks המובילים; הבחירה ב־Vanilla כאן מבוססת על התאמה להיקף, לא על טענה שהוא הפתרון הנפוץ ביותר לכל מוצר.

### 1.2 מגבלות וסיכונים

1. **תמיכת PWA שונה בין דפדפנים ומערכות הפעלה:** אפשרות ההתקנה והדרך להוסיף למסך הבית אינן אחידות, במיוחד ב־iOS; אין להבטיח כפתור התקנה מערכתית בכל דפדפן. יש לבדוק במכשירי Android ו־iPhone אמיתיים.
2. **פתיחת אודיו מוגבלת במדיניות הדפדפן:** ליצור/להפעיל (`resume`) את `AudioContext` בעקבות הקשה יזומה על ״התחל״; לא לצפות להשמעה אוטומטית בעת טעינת הדף. אם ההשמעה נכשלת, המשחק החזותי עדיין צריך לעבוד והתקלה לא תגרום להפסד. באייפון, כשמתג הצד במצב שקט, Safari עלול שלא להשמיע צלילי Web Audio; זו מגבלה ידועה שלא מטפלים בה בקוד, ויש לציין אותה בבדיקות המכשיר.
3. **אחסון מקומי אינו גיבוי:** מחיקת נתוני אתר, גלישה פרטית, מגבלות אחסון או שימוש בדפדפן אחר עלולים למחוק/להפריד תוצאות. יש לטפל בשגיאות גישה וכתיבה ולא להבטיח סנכרון.
4. **Offline מחייב Cache שהושלם:** התקנה או פתיחה ראשונית ללא רשת לא מובטחות; לאחר טעינה מוצלחת ושמירת כל נכסי האפליקציה יש לאפשר שימוש ללא רשת. ניקוי Cache עלול לדרוש טעינה מחודשת ברשת.
5. **GitHub Pages הוא אתר ציבורי:** ב־GitHub Free נדרש Repository ציבורי כדי לפרסם באמצעות Pages; גם באתר מתוך Repository פרטי ברמות מנוי מתאימות, האתר בדרך כלל ציבורי. אין לכלול סודות בקוד. שירות Pages אינו Hosting ל־Backend.
6. **מחיר ומכסות:** לפרויקט סטטי קטן על GitHub Free ו־Repository ציבורי לא צפויה עלות Hosting ישירה. Pages כפוף למגבלות שימוש (למשל מגבלת רוחב פס רכה של 100GB לחודש, וגודל אתר עד 1GB), ולתנאי השירות; מחירים ותנאים יכולים להשתנות.

## 2. ארכיטקטורת המערכת

### 2.1 מבנה כללי

```text
GitHub Repository
  └─ GitHub Actions: Tests → Build (Vite + PWA) → GitHub Pages (HTTPS)
                                                    │
                                             הורדת אתר סטטי
                                                    ▼
                                          דפדפן מובייל / PWA
                     ┌───────────────────────────────────────────────────┐
                     │ UI בעברית (בית, אודות)                           │
                     │ Game Controller ↔ Sequence Engine                │
                     │       │             │                             │
                     │       ├→ Light & Audio Feedback (Web Audio)      │
                     │       └→ Results Repository → localStorage       │
                     │ Navigation / State / Statistics                  │
                     │ Service Worker → Cache של קובצי האפליקציה        │
                     └───────────────────────────────────────────────────┘
```

כל המשחק והמידע פועלים בתוך הדפדפן. GitHub Pages מספק קובצי HTML/CSS/JavaScript ו־Manifest/Service Worker בלבד. אין בקשות רשת במהלך משחק לצורך ביצוע מהלכים, קבלת תוצאות או השמעת צלילים.

### 2.2 שכבות ו־Modules

| Module | אחריות | תלות/ממשק |
|---|---|---|
| `UI / Screens` | ציור מסך הבית והלוח, הודעות ״צפה ברצף״/״תורך!״, מסך ״אודות״, תוצאת סיום, אישור איפוס | מקבל מצב מה־Controller ומעביר אירועים; אינו מחשב ניקוד |
| `Navigation` | מעבר בין שני המסכים בלבד; יציאה מהבית בזמן משחק מבטלת משחק ללא שמירה | מודיע ל־Game Controller על ביטול ומשנה מסך פעיל |
| `Game Controller` | מכונת מצבים, תחילת משחק, הפעלת תצוגת רצף, קבלת לחיצות, מעבר שלבים וסיום | Sequence Engine, Feedback, Results Repository |
| `Sequence Engine` | יצירת צבע אקראי, הוספת צבע לרצף הקיים, השוואת לחיצה לרצף | לוגיקה טהורה, ללא DOM או אחסון |
| `Feedback` | הדלקה זמנית של לחצן ויצירת הצליל המתאים; תמיכה ב־Mute | DOM/CSS, Web Audio API |
| `Results Repository` | קריאת היסטוריה, אימות נתונים, רישום תוצאה רק בסיום, מחיקת נתונים | `localStorage`, עם טיפול בחריגות |
| `Statistics` | חישוב שיא, משחקים שהסתיימו, ניצחונות ואחוז הצלחה | נגזר מהיסטוריית משחקים |
| `PWA / Offline` | Manifest, Service Worker ו־cache לנכסי האתר | `vite-plugin-pwa`, דפדפן; אינו שומר משחק פעיל |

**עיקרון מנחה:** מפרידים בין לוגיקת משחק טהורה לבין DOM, שמע ואחסון. אין צורך ב־State Management Library, Event Bus או שכבת Service כללית נוספת.

### 2.3 מצבי משחק וכללי מעבר

מצבי המכונה:

- `idle`: מסך בית לפני תחילת משחק, כפתור ״התחל״.
- `showing-sequence`: מוצג רצף באופן סדרתי, מוצגת ״צפה ברצף״, הלחצנים חסומים.
- `awaiting-input`: מוצגת ״תורך!״, לחצני הצבעים זמינים; כל לחיצה נבדקת מיד.
- `between-rounds`: השהיה קצרה לאחר הצלחת שלב 1–9, כשהלחצנים חסומים.
- `finished`: ניצחון או הפסד; מוצגים שלבים שהושלמו, שיא והודעת שיא חדש לפי הצורך, ו־״שחק שוב״.

**State זמני בזיכרון בלבד:** `phase`, `sequence: Color[]`, `round` (1–10), `inputIndex`, `completedRounds` (0–10), `muted`, `gameToken` לביטול פעולות מושהות. `Color` הוא Union סגור של `blue`, `red`, `yellow`, `green` (שמות פנימיים בלבד; הממשק בעברית). מצב משחק פעיל לא נכתב ל־`localStorage` או ל־Cache.

**כללים מחייבים:**

1. לחיצה על ״התחל״ יוצרת רצף בן צבע אחד אקראי; ניתן לחזור על אותו צבע מספר פעמים.
2. ההצגה מתבצעת בסדר הרצף, עם משך אור/צליל קבוע והפסקה קבועה בין הצבעים לאורך כל עשרת השלבים. הערכים המספריים הם קבועי מימוש ולא דרישת מוצר חדשה.
3. רק אחרי ההצגה עוברים ל־`awaiting-input`; לחיצות בכל מצב אחר נדחות. יש למנוע גם לחיצות כפולות מהירות/מקביליות שגורמות לעיבוד כפול של אותה אינטראקציה.
4. לחיצה נכונה מקדמת `inputIndex`. לאחר שחזור מלא: אם `round < 10`, מגדילים `completedRounds`, ממתינים מעט, מוסיפים צבע אחד ועוברים לשלב הבא; בשלב 10 מסיימים בניצחון עם ניקוד 10.
5. לחיצה לא נכונה מסיימת מיד בהפסד; התוצאה היא `completedRounds` בלבד, כלומר טעות בשלב 7 מזכה ב־6.
6. פעולת סיום רושמת תוצאה **פעם אחת בלבד**, מחשבת שיא על בסיס ההיסטוריה המעודכנת, ואז מציגה סיכום. ״שיא חדש״ מוצג רק כאשר התוצאה גבוהה ממש מהשיא לפני המשחק.
7. החלפה למסך ״אודות״, רענון או סגירת האפליקציה מבטלים משחק פעיל ללא רישום. חזרה לבית מציגה `idle`.
8. צריך לבטל Timers/אנימציות/אירועי Playback המתייחסים למשחק הישן באמצעות ניקוי והחלפת `gameToken`, כדי למנוע מעבר שלב או השמעת רצף לאחר ביטול/״שחק שוב״.
9. אין Timer שמגביל את זמן התשובה; אין דרישה להאצה. השתקה משפיעה על הצליל בלבד, גם במהלך משחק.

ליצירת צבע משתמשים ב־`Math.random()` (בדיוק אקראי מתאים למשחק שאינו קשור לאבטחה), במיפוי שווה הסתברות לארבעת הצבעים. רצף חדש **לא** נבנה בכל שלב; מוסיפים צבע יחיד.

### 2.4 Data Model ו־Local Storage

מודל רשומה לוגי יחיד:

```ts
type CompletedGame = {
  date: string;                 // ISO 8601 עם תאריך ושעה פנימיים לצורך זיהוי/מיון
  completedRounds: number;      // מספר שלם בין 0 ל-10
  result: 'win' | 'loss';
};

type SavedResults = {
  schemaVersion: 1;
  games: CompletedGame[];
};
```

**מוסכמה:** היסטוריית המשחקים בממשק מציגה *תאריך בלבד*, גם אם ייצוג האחסון הפנימי משתמש בחותמת זמן לצורך סדר הרשומות. אין הצגה של שעה או משך משחק. אם בוחרים לשמור תאריך מקומי בלבד, סדר הרשומות יישמר לפי סדר הוספתן; כך או כך אין שינוי בפיצ'ר.

- מפתח יחיד: `simon:results:v1` המכיל JSON תקין של `SavedResults`.
- מקור האמת הוא `games`; **אין לשמור בנפרד** שיא וסטטיסטיקות, אלא לחשב אותם מהנתונים בעת טעינת ״אודות״ ובסיום משחק. זה מקיים את שמירת השיא בין הפעלות בלי נתונים כפולים.
- `personalBest = max(completedRounds)` או 0 בהיסטוריה ריקה; `totalGames = games.length`; `wins = count(result === 'win')`; `winRate = Math.round(wins / totalGames * 100)` כשיש משחקים, ובאין נתונים מוצג ״אין נתונים״.
- תצוגת ההיסטוריה ממוינת מהחדש לישן; התאריך מוצג בפורמט `DD.MM.YYYY` לפי שעון המכשיר.
- ניתן לשמור רק הפסדים עם ניקוד 0–9 וניצחונות עם 10; יש לאמת טווחים וסוגים בקריאה כדי למנוע קריסה עקב נתונים משובשים.
- כתיבה היא `read → append → JSON.stringify → localStorage.setItem` רק בסיום משחק; אין שינוי נתונים בעת נטישת משחק. שגיאת כתיבה (`QuotaExceededError`/`SecurityError`) לא תמנע הצגת תוצאת המשחק; יוצג משוב בעברית שהתוצאה לא נשמרה, והשיא המוצג לא יוצג בטעות כשיא שנשמר.
- במקרה של נתוני JSON פגומים או גרסה לא נתמכת: אין לדרוס אותם אוטומטית; יש להציג מצב נתונים לא זמין/לא תקין בעברית ולשמור על יציבות האפליקציה. איפוס מאושר יכול למחוק את מפתח הנתונים ולחזור למצב ריק.
- אישור ״איפוס נתונים״ מפעיל `removeItem` למפתח האפליקציה בלבד; ביטול לא משנה דבר. לא להשתמש ב־`localStorage.clear()` כדי לא למחוק נתוני אתרים/יישומים אחרים באותו Origin.
- כל הנתונים מוגבלים לדפדפן/Origin/הקשר אחסון. אין סנכרון בין התקנת PWA, דפדפן אחר או מכשיר אחר אם סביבת ההפעלה אינה משתפת אחסון.

### 2.5 ממשקים וזרימת מידע

**זרימת משחק:**

```text
לחיצה על ״התחל״ → Controller יוצר רצף → UI מציג ״צפה ברצף״
→ Feedback מפעיל אור וצליל לכל צבע → UI מציג ״תורך!״
→ אירוע לחיצת צבע → Controller בודק מול Sequence Engine
    ├─ טעות → סיום בהפסד → Results Repository שומר → Statistics מחשב → UI מציג תוצאה
    ├─ סיום שלב 1–9 → השהיה → הוספת צבע → הצגת הרצף המלא
    └─ סיום שלב 10 → ניצחון → Results Repository שומר → Statistics מחשב → UI מציג תוצאה
```

**זרימת אודות:** מעבר למסך → Controller מבטל משחק פעיל אם ישנו → Results Repository קורא היסטוריה → Statistics מחשב נתונים → UI מציג הסבר, הוראות, שיא, היסטוריה וסטטיסטיקות → אפשרות אישור איפוס.

**API Contracts פנימיים בלבד:** אירועי `startGame`, `pressColor(color)`, `navigate(screen)`, `setMuted(boolean)`, `requestReset`, `confirmReset`, וקריאת `getHistory`/`getStatistics`. אין HTTP API או חיבור לרשת לצורכי המשחק.

### 2.6 UX, נגישות ומובייל

- HTML מוגדר `lang="he"` ו־`dir="rtl"`; כל טקסטי הממשק בעברית בלבד. אין מערכת תרגום.
- תכנון למסכי טלפון באמצעות `viewport` מתאים, CSS Grid של 2×2, לחצני מגע גדולים עם `button` סמנטי, הפרדה ומצבי `disabled` אמיתיים בזמן הצגת רצף.
- להשתמש ב־CSS logical properties לשמירה על כיווניות; נתונים דוגמת מספרים מוצגים באופן ברור.
- הודעות המצב והתוצאות הן טקסט, לא צבע/צליל בלבד. יש לדאוג ל־focus נגיש, תוויות ברורות ללחצנים ולכפתור השתקה, ומשוב לחיצה חזותי. שימוש ב־`aria-live` למסרי מצב קצרים מתאים, תוך מניעת הכרזות חוזרות של כל הבהוב.
- אפקט הדלקה יופעל באמצעות CSS classes ויסתיים לאחר זמן קבוע; אין להסתמך על `:active` בלבד משום שהצגת הרצף אוטומטית.
- במצב Offline או Mute עדיין נשמרים כל כללי המשחק והמשוב החזותי.
- התאמה ייעודית ל־Tablet/Desktop אינה חלק מההיקף; אין לחסום בהכרח פתיחה בהם, אך בדיקות UX מתמקדות במובייל.

### 2.7 PWA, Cache ו־Offline

- הפעלת `vite-plugin-pwa` במצב `generateSW` כדי לייצר Web App Manifest ו־Service Worker מבוסס Workbox.
- Manifest כולל `name` ו־`short_name` בעברית, אייקונים מקומיים מתאימים (לרבות 192×192 ו־512×512 וגרסה מתאימה להתקנה), `display: standalone`, `start_url` ו־`scope` לפי נתיב הפריסה של האתר. אין צורך בשרת Push/Notifications.
- אסטרטגיה: **precache של כל נכסי ה־Build הדרושים לתפעול המשחק** — HTML, JS, CSS, קובצי הגופן Rubik (`woff2`), Manifest/Icons, וכל נכס סטטי מקומי — בתוספת fallback למסמך הראשי לצורך פתיחה מתוך נתיב האפליקציה. אין תלות ב־CDN, Google Fonts, קובצי שמע חיצוניים או בקשות API.
- בפריסת GitHub Pages תחת `/<REPO>/`, לוודא שה־`base` של Vite, `start_url`, `scope`, נתיבי האייקונים ו־Service Worker עקביים; להימנע מנתיבים מוחלטים לשורש הדומיין שאינם כוללים את שם ה־Repository.
- לכל גרסת Build יש Cache מנוהל עם ניקוי נכסים ישנים. גרסה חדשה לא תחליף קובצי משחק פעיל באמצע סיבוב; ניתן להחיל עדכון בהפעלה/טעינה הבאה. אין דרישה לתיבת הודעת עדכון או מסך נוסף.
- בדיקה מחייבת: לפתוח את האתר פעם אחת עם אינטרנט, לוודא ש־Service Worker שולט בדף ושה־precache הושלם, לעבור ל־Offline ולבצע פתיחה חוזרת, משחק מלא, שמירה וצפייה בהיסטוריה.
- Cache Storage של ה־Service Worker מאחסן **נכסי יישום**, ואינו משמש לאחסון היסטוריית משחקים או מצב משחק.

### 2.8 אבטחה ופרטיות

- אין משתמשים, הרשאות תפקיד או Authentication; המשחק אינו ניגש לנתונים פרטיים ממכשיר המשתמש מעבר לתוצאות שהוא מייצר.
- GitHub Pages מספק HTTPS; Service Worker מחייב הקשר מאובטח (או `localhost` בסביבת פיתוח).
- להימנע מ־`innerHTML` עם נתונים לא מהימנים; להשתמש ב־`textContent` וביצירת DOM בטוחה. לבצע בדיקת תקינות ל־JSON הנקרא מאחסון.
- אין Tokens, מפתחות API או סודות בצד הלקוח או ב־Repository. GitHub Actions משתמש בהרשאות הפריסה המינימליות הדרושות.
- רק היסטוריית משחקים מקומית; אין Analytics או העברת תוצאות למפעיל האתר. GitHub Pages עשוי לעבד לוגי גישה במסגרת השירות, בנפרד מהאחסון המקומי.
- אחסון מקומי אינו נחשב מנגנון חסין לשינוי: משתמש יכול לערוך נתונים דרך כלי דפדפן, וזה מקובל במשחק יחיד ללא מערכת ניקוד ציבורית.

### 2.9 GitHub, סביבת פיתוח ו־Deployment

**Repository:** Repository יחיד ב־GitHub. `main` הוא ענף האתר המתפרסם; קוד המקור, קובצי תצורה, בדיקות וקובץ נעילת חבילות מנוהלים ב־Git. לא להעלות `node_modules`, `dist`, קבצים מקומיים או פרטי גישה.

**Development:** עבודה מקומית עם Node.js LTS ו־npm, הרצת Vite בשרת פיתוח מקומי. אין Docker, Database או שירות ענן הנדרש לצורך בדיקות משחק. לבדיקה מדויקת של Service Worker יש להריץ גם Build מסוג Production ב־localhost או לבדוק בכתובת HTTPS שפורסמה; מצב Dev לבדו אינו תחליף לבדיקת Offline.

**Production / GitHub Pages:**

1. הגדרת GitHub Pages כך שמקור הפרסום יהיה **GitHub Actions**.
2. כל Push לענף `main` מפעיל Workflow ב־GitHub Actions עם הרשאות `contents: read`, `pages: write`, `id-token: write`.
3. ה־Workflow מבצע Checkout, התקנת Node.js LTS, הרצת `npm ci`, בדיקות Vitest, `npm run build` ובדיקות אוטומטיות שהוגדרו עבור Build; רק אם עברו, מעלה את תיקיית `dist` כ־Pages Artifact ומפרסם באמצעות `actions/deploy-pages`.
4. כתובת האתר היא `https://<OWNER>.github.io/<REPO>/` בפרויקט רגיל (או דומיין מותאם אם יוגדר בהמשך); `vite.config` מגדיר `base: '/<REPO>/'` לפריסה בנתיב זה. בפרויקט זה ה־Repository הוא `alonk0/simon`, ולכן הכתובת הצפויה היא `https://alonk0.github.io/simon/` וה־`base` הוא `'/simon/'`. במקרה של דומיין שורש מותאם, לעדכן את `base` ל־`/` ולהתאים Manifest ו־Scope.
5. רצוי למנוע פריסות מקבילות לאותו יעד ולהשתמש ב־Workflow עם `concurrency` לפריסה. שינוי קוד שלא עבר בדיקות לא יפורסם.

לשם בדיקות משתמש מוקדמות ניתן להפעיל שרת פיתוח מקומי או לצפות בגרסת Pages שפורסמה; אין חובה להקים סביבת Staging נפרדת. פריסות Production הן סטטיות ולכן אין צורך ב־Environment Variables או Secrets יישומיים.

### 2.10 בדיקות וקריטריוני תקינות טכניים

**Vitest – לוגיקה:** רצף מתחיל באורך 1 וגדל עד 10; צבעים נבחרים מתוך ארבעה ויכולים לחזור; רצף קודם אינו משתנה; לחיצה שגויה מסיימת מיד; ניקוד 0 בטעות בשלב 1 וניקוד 6 בטעות בשלב 7; ניצחון אחרי הצלחת שלב 10; שמירה בדיוק פעם אחת; איפוס/ביטול; אחוז הצלחה בהיסטוריה ריקה; שיא חדש רק בשיפור ממשי; בדיקת נתונים לא תקינים ושגיאת אחסון. להזריק מקור אקראיות ושעון ניתנים לשליטה בבדיקות, בלי לשנות את האקראיות האמיתית במוצר.

**בדיקות מכשיר אמיתי:** Chrome ב־Android ו־Safari/iOS עם אפשרות Add to Home Screen: הקשה על ״התחל״ משחררת AudioContext; צלילים מובחנים; התאמה לרוחב מסך קטן; התקנה/פתיחה עצמאית; Offline לאחר Cache; התמדה/מחיקה של `localStorage` בהתאם להתנהגות סביבת ההפעלה. בדיקת Playwright המדמה מכשיר אינה מבטיחה התנהגות התקנה או אודיו זהה במכשיר אמיתי.

## החלטות מרכזיות (ADRs)

### ADR-1: קבועי זמן להצגת הרצף
**הקשר:** ה־PRD וה־ARCHITECTURE דורשים קצב הצגה קבוע וקצר בכל השלבים, בלי לקבוע מספרים.
**החלטה:** ב־`src/game/timing.ts`: השהיה לפני הצבע הראשון 600ms, הדלקה + צליל לכל צבע 500ms, הפסקה בין צבעים 250ms, הדלקה + צליל ללחיצת שחקן 250ms, השהיה בין שלבים 800ms. אין מגבלת זמן לתשובת השחקן.
**השלכות:** שינוי קצב נעשה במקום אחד. הצגת שלב N נמשכת `600 + N·500 + (N−1)·250` ms; משחק ניצחון מלא אורך כדקה.

### ADR-2: אקראיות דטרמיניסטית בבדיקות
**הקשר:** בדיקות זרימה צריכות רצף צפוי, בלי לשנות את האקראיות במוצר.
**החלטה:** ה־Game Controller מקבל פונקציית `random` (ברירת מחדל `Math.random`). Vitest מזריק פונקציה נשלטת ומשתמש ב־fake timers; Playwright מחליף את `Math.random` בדף באמצעות `page.addInitScript`.
**השלכות:** קוד המוצר אינו מכיל מצב בדיקה. מסלול הניצחון המלא (10 שלבים) נבדק ב־Vitest ולא ב־Playwright, כדי לשמור על בדיקות ממשק מהירות.

### ADR-3: חיבור התוצאות השמורות לסיום המשחק
**הקשר:** בסיום משחק יש לרשום תוצאה פעם אחת, להציג שיא אישי ו״שיא חדש!״ רק בשיפור ממשי, ולא לדווח על שמירה שנכשלה.
**החלטה:** ה־Game Controller אינו תלוי באחסון; הוא מקבל `onFinish` שנקרא פעם אחת בלבד ב־`finish()` (לא ב־`cancel`), והתוצאה (`saved`, `personalBest`, `isNewBest`) נכנסת ל־state לפני הצגת החלונית. `main.ts` מחשב את השיא לפני הרישום ואחריו (`src/game/statistics.ts`), ו־`src/storage/resultsRepository.ts` הוא היחיד שניגש ל־`localStorage`. כשהשמירה נכשלת: מוצג רק השיא השמור הקודם (או לא מוצג שיא כשאין גישה לנתונים), בלי ״שיא חדש!״, עם ״התוצאה לא נשמרה במכשיר״. נתונים לא תקינים אינם נדרסים.
**השלכות:** ה־Controller נשאר בדיק בלי אחסון. תוצאה שלא נשמרה לא משפיעה על השיא המוצג. משחק ראשון עם 0 שלבים אינו ״שיא חדש״. ב־Milestone 4 ישתמש מסך ״אודות״ באותם `load`/`clear` ו־`computeStatistics`.

### ADR-4: מסך ״אודות״ ו־Dialog האיפוס
**הקשר:** מסך ״אודות״ צריך להציג נתונים תואמים לאחסון, היסטוריה מהחדש לישן, ואיפוס רק לאחר אישור — כשכבה ולא כמסך נוסף.
**החלטה:** ה־Dialog ממומש באלמנט `<dialog>` המובנה (`showModal()`), שמספק Overlay, מיקוד בתוך החלון ו־Escape כביטול. ״אודות״ קורא מחדש את `load()` ומחשב `computeStatistics` בכל כניסה ובכל איפוס. סדר ההיסטוריה נגזר מהיפוך סדר ההוספה ולא ממיון לפי תאריך. מצבי אחסון ״לא זמין״/״לא תקין״ וכישלון איפוס מוצגים כהודעה בכרטיס ההיסטוריה, והכרטיסים מציגים מצב ריק.
**השלכות:** אין קוד ניהול מיקוד ידני. משחקים מאותו יום נשארים בסדר הנכון. נתונים פגומים אינם נדרסים עד לאיפוס מאושר, ואין דיווח כוזב על איפוס שנכשל.

### ADR-5: עדכון Service Worker, אייקונים ובדיקות מול Build
**הקשר:** גרסה חדשה לא תחליף קבצים באמצע משחק ואין דרישה להודעת עדכון (§2.7); נדרש לבדוק `base`, Manifest ו־Offline כפי שיפורסמו; iOS אינו משתמש באייקוני ה־Manifest למסך הבית.
**החלטה:** `vite-plugin-pwa` עם `registerType: 'prompt'` וללא UI — Service Worker חדש ממתין ונכנס לתוקף בפתיחה הבאה. Service Worker פועל רק ב־Build (`devOptions.enabled: false`). Playwright רץ מול `vite preview` של ה־Build (`http://localhost:4173/simon/`), כולל בדיקת Offline עם `context.setOffline`. אייקוני ה־PNG (192, 512, maskable ו־`apple-touch-icon` 180) מופקים מקומית מ־`public/*.svg` בסקריפט `npm run icons` (Chromium של Playwright, ללא תלות נוספת) ונשמרים ב־Repository.
**השלכות:** משתמש שהאפליקציה פתוחה אצלו לאורך זמן יקבל עדכון רק אחרי סגירה ופתיחה. בדיקות הממשק איטיות מעט (Build לפני ההרצה) אך בודקות את מה שמתפרסם בפועל. שינוי באייקון מחייב הרצת `npm run icons`.
